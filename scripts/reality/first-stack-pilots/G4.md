# G4 disk-backed IO contract campaign

This adapter reuses the pilot's immutable PostgreSQL/Bun image pins, telemetry,
native raw volume, external capture, binary artifact hashes and LF-normalized
source identity. It requires no cloud account or paid services. It creates one
internal network with no published ports, one PG data volume and one raw volume.
Disposable trust authentication is restricted to that fixture. At most one
PostgreSQL, observer and pgbench group runs at a time: 3 CPUs / 4096 MiB total,
swap disabled, 128 PIDs per container. It records selected Docker limit fields;
it does not capture container environment variables.
Sources: `g4-manifest.json:1`; `g4-run.ts:1`.

Four custom SQL files run point reads, random independent updates, one hot-key
update and 32-row indexed ranges. One SQL statement is one implicit autocommit
transaction; sessions persist within warmup/observation. Clients are fixed at 1
or 8, prepared mode, one pgbench thread; no app pool, TLS, reconnect-per-query,
rate control, retries or open-arrival schedule. Each dataset gets a seeded
randomized 4-operation × 2-client × 3-repeat sweep. Five seconds of warmup precede
ten seconds of observation in a separately reconnected phase. These deliberately
short windows stay within the shared-laptop characterization budget and do not
replace the longer rate/steady/recovery campaign proposed in the Stage 2 plan.
Eight clients is a whole-level holdout; no fit or Model 2 comparison occurs.
The campaign has a 30-minute hard stop; each Docker invocation has a watchdog.
Sources: `g4-manifest.json:23`; `g4-run.ts:7`.

The server pins shared buffers at 32 MiB, fsync and synchronous_commit on,
tracks IO/WAL timing, preloads pg_stat_statements and leaves checkpoint/autovacuum
enabled with logging. New datasets use 8192 and 524288 keys, 256-byte values,
fillfactor 90, an integer primary key and a bigint update counter. Initialization
includes VACUUM ANALYZE and CHECKPOINT; EXPLAIN ANALYZE/BUFFERS/WAL/SETTINGS plans
are retained separately. EXPLAIN update probes commit one update before the
sweep; counters reflect that history. Tables are not restored between cells, so
updates, page warming, bloat and background work are part of the recorded order.
There is no cold OS-cache assertion.
Sources: `g4-run.ts:46`; `g4-point-read.sql:1`; `g4-range-read.sql:1`.

Snapshots bracket whole windows (including warmup/overhead), retaining database,
pg_stat_io, WAL, checkpointer/bgwriter, tables and pg_stat_statements, plus PG
cgroup CPU/throttle/memory/IO/pressure and shared Linux diskstats. An observer
samples pg_stat_activity every 250 ms; sample lateness is not corrected into
invented durations. Raw pgbench output retains complete aggregate successful/
failed observation counts and 1% sampled transaction logs. The sample is not a
complete root trace or a tail-accuracy proof. Per-window generator cpu.stat and
memory.events reveal generator throttling/OOM; initial connection time is kept
apart from transaction mean latency. CPU runnable time, app pool waiting and
per-query CPU are Unknown.
Sources: `g4-run.ts:38`; `g4-probe.ts:1`; `g4-summary.ts:1`.

Run from the repository root with Bun 1.3.14 and the existing pinned images:

```powershell
bun --no-env-file scripts/reality/first-stack-pilots/g4-run.ts C:/external/new-g4
bun --no-env-file scripts/reality/first-stack-pilots/archive.ts C:/external/new-g4
bun --no-env-file scripts/reality/first-stack-pilots/g4-summary.ts --write C:/external/new-g4
bun --no-env-file scripts/reality/first-stack-pilots/g4-summary.ts --raw C:/external/new-g4
bun --no-env-file scripts/reality/first-stack-pilots/g4-findings.ts --write
bun --no-env-file --no-install test scripts/tests/g4Pilot.test.ts
bun --no-env-file node_modules/typescript/bin/tsc --noEmit -p scripts/reality/first-stack-pilots/tsconfig.json
```

Static CI verification needs no containers/raw data: `g4Pilot.test.ts` verifies
the pinned summary, sources, limits, dataset relations and forbidden promotion,
and regenerates findings in memory. `g4-summary.ts` and `g4-findings.ts` without
arguments also check their pins. Failures are retained; structural verification
can pass with `campaignResult: incomplete-retained`, which never means successful
measurement. Current campaign results are in
`docs/reality/g4-local-findings.md:1`; the raw manifest pins every external file.

The reviewed proposal for 07b is `docs/reality/finite-io-contract.md:1` with a
structural draft schema. Neither is wired to an engine validator/compiler. No
production TypeScript, execution identity, activation, historical calibration,
UI or timing label changes. G1/G5 and historical tmpfs evidence remain separate.
