# Returning database process after promotion

The optional saved Database setting `databaseReplication.rejoin: "snapshot-replay/1"` selects captured adapter profile `db-rejoin/1`. Omit it to retain the original promotion behavior and recorded output. Existing published challenges do not select this setting. There is no new lab or inspector control in this slice.

The model has two processes, one explicit promotion and one replacement replica incarnation on the original primary process. At promotion, the original writer remains fenced. The model captures the promoted writer's authoritative row snapshot and queues subsequent atomic committed write batches in order. The new logical member identity contains the resource id, original-primary process label and new writer epoch. Historical member labels stay stable; the original `replica` process is now the writer.

On return, the old primary stays fenced while the snapshot and queued commits replay. The snapshot replaces all old rows, including divergent higher versions and keys absent from the promoted writer. It cannot restore acknowledgements already recorded as lost at promotion. Each snapshot or commit batch takes one saved replication delay in simulated time, serially. Either process being unavailable cancels the scheduled batch; resumption restarts that batch's full educational delay. Replay never runs while either process is down.

After the first full replay the old process has role `replica`. Later commits continue to queue and replay; this role survives subsequent outages. `eligible` means available, source writer available, snapshot applied and no pending batches at this sample. It does not admit a second promotion, route reads to the returned process or promise continuous health. The old writer role and old writer epoch never regain authority. During an outage there can be no available writer; whenever writer work is available, exactly one process owns it.

Saved optional `rejoin` evidence records the new identity/epoch, availability, state, snapshot rows/applied flag, pending batches (snapshot included), new-writer committed/replayed/pending operations, eligibility and first full rejoin time. Counts reconcile as committed = replayed + pending. The original `pendingReplication`, generations, `lostOperations` and `regressedKeys` retain their original populations; zero old pending work is never preservation evidence. `primaryEpoch` becomes the new epoch when the authoritative snapshot is installed. Missing measurements stay Unknown (`null`); an omitted lifecycle field stays omitted on historical reports.

This is an educational snapshot and ordered replay mechanism bounded by existing row, request and event limits. Exceeding an engine budget fails explicitly as incomplete evidence. It is not physical replication timing, PostgreSQL/MySQL protocol fidelity, disk/WAL recovery, a durable commit log, consensus, multi-replica quorum, split-brain resolution, automatic election, application correctness or a preservation guarantee.
