# Saved capabilities added in the next-lane window

These notes cover optional saved settings captured as named adapter profiles, plus predictions and diagnosis labs using existing evidence. Omitting an optional setting keeps the earlier compiled bytes, published hashes and recorded output. Every setting is an educational authored input, never a measured provider behavior, and missing evidence stays Unknown rather than zero.

## DNS single-name publication (`dns-publication/1`)
Saved DNS setting `dnsPublication {version 1, initialRecord "absent"}`. The one modeled name starts without a record; a scripted publish makes the first answer possible, and resolver negative caching then decides when callers can resolve it. Evidence is the authority and resolver summaries and the first successful answer time. Limits: one name, no delegation hierarchy, CNAME, DNSSEC, failover or health routing. A first successful answer is not first admitted traffic, continuous health or a propagation benchmark. Established connections keep their binding.

## Artifact cache capacity (`artifact-cache/1`)
Saved `artifactCachePolicy {version 1, capacityBytes}` on an autoscaled VM binds one byte capacity to every owned artifact client. An initial deployed replica stays ready without a pull; later replicas acquire the assumed layer. A layer larger than the remaining capacity is refused with `node-blob-cache-capacity`, and retries cannot make it fit. Capacity failure can never mark an artifact or listener ready. Limits: one assumed layer, no image-pull speed or network transfer model, no eviction, prewarming, shared-host reuse or rollout. The `startup-capacity` criterion counts later replicas with a measured listener that are currently load-balancer eligible at one second; it does not show continuous health or first traffic.

## Autoscaling from delivered samples (`autoscaling-observed/1`)
Saved autoscaling `signal {version 1, source "observed-core-time", monitorId, freshForSeconds, stale "hold"}`. The pool controller scales only on core-time samples the named monitoring backend has received within the freshness bound; missing, old or incomplete samples hold the current desired count. Limits: one source and one stale policy, freshness at most 60 seconds, no provider metric semantics, no scale-down guarantee. Delivery cadence and buffering belong to the monitoring settings.

## Gateway quota scope (`gateway-quota/1`)
Saved `gatewayQuota {version 1, scope "shared" | "per-route"}` on an API Gateway with at least two explicit routes whose burst and refill are equal. Shared means one token bucket for all routes; per-route means one per route. Limits: equal budgets only, no weighted fairness or starvation guarantee, no tenant or key identity. Results show coupling between routes under a fixed workload, not general fairness.

## Worker external wait (`worker-wait/1`)
Saved `asyncWorker.externalWaitMs` (0 to 60000) adds a per-job wait after CPU work. The job keeps its parallel slot, prefetch credit and lease but spends no CPU while waiting. Limits: one authored wait for every job of that worker, no connection pool, timeout, retry or provider behavior on the outside call, no per-class slow jobs, a larger VM adds cores and not slots.

## Queue repair and redrive (`queue-redrive/1`)
Saved `asyncWorker.repairAtSecond` stops poison selection at that second; saved `asyncQueue.redriveAtSecond` returns dead-lettered messages to ready once at that second. Redriving before the repair re-dead-letters them. Limits: one timed repair and one redrive, no new message identity beyond the existing receipt rules, no ordering, exactly-once or durability claim, and cumulative dead-lettered counts are not current dead-letter depth.

## Cache write invalidation and freshness (`cache-invalidation/1`)
Saved `cachePolicy.invalidateOnWrite` (boolean, either value is captured; omitted keeps today's behaviour, which invalidates). When on, a committed write removes the cached row; when off the old row stays until its TTL ends. Marked designs also record freshness: a cache hit is counted as behind the database when its row version is older than the version the one unreplicated database had committed for that key at that moment (`Cache: Hits behind the database`, `Cache: Most versions behind`; 0 versions means none was behind, null is Unknown). `refresh-after-a-write` marks both values so the starter, the reference and the TTL near miss share one adapter selection. The `cache-fresh-reads` criterion requires a bound on hits behind the database and a minimum number of hits, so a cache that rarely hits does not pass. Limits: version lag in the model, not application correctness or read-your-writes; one cache, one row per request, invalidation is a delete after the commit so the brief gap can still show a few hits behind; a replicated or read-routed database is refused, not guessed; typed application-flow cache steps still require invalidation on.

## Row lock order and deadlock evidence (`row-lock-order/1`)
Saved Database setting `rowLocking {version 1, rowsPerWrite 2, order "as-requested" | "by-key"}` (needs a saved data keyspace of at least two rows; both values are captured; omitted keeps today's single-row write byte for byte). A marked write is two row updates, 2 ms then 1 ms of database CPU (authored), and keeps the exclusive lock on the first row while it works on the second. The second row is drawn deterministically from the other rows. As requested takes the two rows in the order drawn; by key takes the lower-numbered row first, so a wait-for cycle cannot form. Marked databases record `Deadlocks detected`, `Row-lock waits` and `Transactions ended as deadlock victims` (0 when none, null when never measured). The `database-deadlocks` criterion bounds the deadlocks and is not evaluated when the saved order, the counters or the exact second are missing or contradictory. Limits: an educational model of the order a transaction touches rows, with no claim about any database product's lock manager, deadlock timeout or victim choice (the model finds a cycle immediately and ends the requesting transaction); two rows per write, exclusive locks only, no retry after a deadlock; a replicated or read-routed database, a cache in front of the database and typed application flows are refused, not guessed. Ordering is an application convention. Spreading the same traffic over many more rows also makes a cycle unlikely, which `order-the-row-locks` states as a valid but probabilistic alternative.

## Load balancer admission in use (`lb-admission/1`, existing)
`lbAdmission {maxActive, maxQueued, queueWaitMs}` already compiled; two labs now use it. Lowering Active requests sheds excess demand and bounds the tail of admitted requests; raising it opens a forwarding gate that was serializing spare backend capacity. Limits: admission chooses who waits and adds no capacity; clients that back off are not modeled.

## Replica staleness evidence (`stale-reads` criterion, existing saved delay)
The saved `databaseReplication.replicationDelayMs` (1 to 60000) already set how long a replica applies each writer commit after it. Read routing records `staleReads` and `maxStaleReadAgeMs`. The `stale-reads` challenge criterion compares the cumulative stale read count at one exact second with a bounded limit and is not evaluated when the named replicated database, the exact second or the counters are missing or malformed. Limits: counters are cumulative, include health probes and describe modeled row versions only; the delay is an authored constant, so a real replica's varying lag is not modeled; nothing here shows application consistency or read-your-writes.

## Cache capacity and lifetime in use (`data-cache-capacity/1`, `data-cache-policy/1`, existing)
`cachePolicy {version 2, capacityEntries, ttlSeconds, singleFlight}` already compiled. `fit-the-working-set` uses capacity when a uniform working set exceeds the cache (evictions), the mirror of `reuse-before-expiry` (expiry with room to spare). A TTL of 60 seconds is the unmarked default; any other TTL is captured as `data-cache-policy/1`, so a design pair must differ in TTL consistently or the comparison degrades to side-by-side. Limits: counters are cache commands, not a caller hit ratio; no writes, invalidation or freshness requirement; entries are logical.

## CDN single shared origin fetch (`cdn-coalescing/1`, existing)
`cdnCachePolicy {version 2, ttlSeconds, coalesce, maxWaiters}` lets requests that miss the same object during a refill share one origin fetch. `share-one-origin-fetch` compares origin requests with coalescing off and on. Limits: one object, fixed request rate and object size, no geographic edges, purge propagation or stale serving; fewer origin requests show no freshness or user-impact result by themselves.

## Serverless warm-instance retention (`serverless/1`, existing `idleExpiryMs`)
`serverless {version 1, concurrency, initializationMs, durationMs, timeoutMs, idleExpiryMs}`. A call after the idle window pays initialization again. `keep-a-function-warm` separates idle expiry from a concurrency ceiling using the `function-reuse` criterion (completed calls, cold starts, unsuccessful calls). Limits: exact idle retention is an educational saved control, not a provider contract; the first call is always cold; function CPU, memory and cost are not modeled; no prewarming or provisioned concurrency.

## Event bus dead-letter capacity (`event-bus/1`, existing `deadLetterCapacity`)
`eventBus {version 1, retryDelayMs, maxAttempts, deadLetterCapacity}`. After the delivery attempts are used, the dead-letter list is the only retained copy of a failed event; a full list discards the rest. `keep-failed-events` uses the `bus-dead-letters` criterion. Limits: one subscriber failure mode, no redrive for the bus, no ordering or exactly-once claim; raising attempts does not enlarge the list.

## Monitoring collection interval (`monitor-cadence/1`, existing `collectionIntervalSeconds`)
`monitoringPolicy {version 2, collectionIntervalSeconds, exportIntervalSeconds, bufferSamples, batchSamples, exportAttempts}`. A sample cannot be newer than the last collection, so exporting more often does not freshen it. `sample-often-enough` changes only the collection interval. Limits: one agent and backend, authored cadences, no provider metric resolution, no alert evaluation; delivery of one sample is not continuous coverage.

## Multi-cause cascade tracing (`trace-a-slowdown-cascade`)
An executable diagnosis lab over existing evidence: Single-flight already shares same-key fills, but a one-entry cache evicts values across sixteen keys before their TTL ends. A scripted database CPU cut makes those source reads contend, causing downstream timeouts and caller loss. Increasing cache capacity retains warm keys during the cut. The unchanged no-slowdown control passes; retries mitigate loss here rather than cause it. It adds no saved setting. Limits: fixed data demand and one scripted incident; cumulative caller outcomes and retained samples do not establish continuous recovery, root-cause automation or a general remedy. Narrowing demand to one key also passes, as the lesson discloses.

## Reuse successful empty queries (`cache-negative/1`)
`cachePolicy.negativeTtlSeconds` is optional on both cache-policy versions: 0 explicitly disables absence caching, and 1 to 3600 seconds retains successful empty query results. Both values capture the profile. `dataKeyspace.absentCount` optionally leaves that many keys, at the end of the bounded key list, without initial rows; valid empty queries already existed in the database engine. These inputs support a static read-only dataset. Writes, typed flows, replication, read routing and row locking are refused; negative caching with stale fallback or write-freshness tracking is refused too. Inserts and mutable absence visibility are not modeled.

Absence entries carry no invented row version or body. They own real modeled entry overhead, share LRU capacity with row bodies, expire at their own TTL and obey invalidation/flush generation tokens. Errors, missing reply bodies and out-of-dataset rejections never prove absence. Marked cache reports retain successful absent answers, negative hits and successful empty source queries, summed over targeting helpers; missing helper evidence stays Unknown. Source queries and answers differ when fills coalesce. `cache-an-empty-answer` scores a finite-horizon source-work ratio alongside caller outcomes, without requiring an exact hit count or a particular lifetime. There is no HTTP, provider timing, Bloom filter or distributed coherence claim.

## Load balancer rate limit in use (`lb-rate-limit/1`, existing)
`lbRateLimit {version 1, burstRequests, sustainedRequestsPerSecond}` is a token bucket at the balancer: the burst is spent first, then admission follows the sustained refill. `set-the-limit-above-the-peak` uses a scripted legitimate peak above the sustained rate; refusals appear as failed callers while app CPU stays low. Limits: one bucket for all callers, no per client identity, fairness or abuse model; a rate limit is a policy, not capacity, and no availability guarantee follows from one run.

## Retained cache answers after expiry (`cache-stale/1`)
Saved `cachePolicy.staleSeconds` bounds how long a retained body may answer after expiry when its database refill fails. `serve-stale-on-error` keeps the normal TTL fixed and scores caller outcomes plus stale answers and maximum age past expiry. Answers are counted per waiting helper request, not per unique caller; failed fills include successful database replies without a row, so a deleted row can still fall back to an older body. Limits: age is measured past expiry, not since the body was fetched; no application correctness or real cache guarantee follows. Missing stale evidence stays Unknown.

## Application CPU budget in use (`vm-cpu-quota/1`, existing)
Saved `vmCpuQuota {version 1, limitPercent}` gives VM work a percentage of total modeled core capacity in fixed CPU-budget windows. `release-the-cpu-budget` compares releasing that budget with adding worker slots that still share it. Reports retain the saved percentage, CPU and cumulative caller outcomes; scheduler throttled time is not retained. Limits: an authored model budget, not an operating-system or provider quota; a larger instance also passes this fixed workload, and raising a quota is not a universal instruction to remove isolation.

## Busiest-resource prediction (`busiest-resource`)
This prediction chooses a captured resource id by its highest terminal CPU measurement, accepting any tied id. It requires current-revision evidence and finite CPU for every offered resource. Load balancers and firewalls are excluded from Model 2 choices; another offered resource without measured CPU leaves the answer Unknown because an unseen higher value cannot be ruled out. It adds no saved setting and does not identify the first bottleneck, highest latency, or a causal root cause.

## Trace a burst backlog (`trace-a-burst-backlog`)
An executable diagnosis lab follows failed uploads back to refused queue publishes during a burst. Increasing saved queue capacity retains more events for the unchanged worker to drain; a refused publish never creates an event to recover later. Saved cumulative caller outcomes and queue acknowledgements are scored together. A modest worker increase still fails, while a much faster worker or cheaper jobs can prevent the queue filling and also pass. Limits: existing queue and worker settings, no new engine mechanism, producer retries, physical durability or exact drain-time guarantee.

## Trace a scaling stall (`trace-a-scaling-stall`)
An executable diagnosis lab follows caller failures through app CPU, desired pool size, controller evaluations and delivered-sample age back to the monitor's export interval. Shortening only that interval supplies fresh measurements to the existing observed-core-time controller; the lab scores in-service replicas and cumulative callers. Raising the replica ceiling or artifact capacity does not repair the missing signal. Limits: fixed collection and export cadences, freshness bound and roomy artifact cache; loosening freshness can also permit scale-out but still misses this lab's caller requirement. No real autoscaler timing or continuous availability is established.

## What these notes do not claim
No capability here implies cloud-provider fidelity, an availability guarantee, a whole-run latency target or cost accuracy. Each lab reads fixed-second samples and states its own limitations in its lesson.
